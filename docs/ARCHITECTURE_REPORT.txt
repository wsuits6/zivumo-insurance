3. FRONTEND ARCHITECTURE
================================================================================

3.1 Application Model
---------------------
This is a Multi-Page Application (MPA). Each page is a standalone HTML file.
Navigation between pages causes full page reloads. There is no client-side
router.

3.2 Page Categories
--------------------
Category              Pages                              Auth Required
---------------------  ---------------------------------  ---------------
Public/Landing         index.html                         No
Auth                   login.html, signup.html            No
User App               dashboard.html, policies.html,     Yes (JWT)
                       policy-details.html,
                       policy-renew.html, new-policy.html,
                       documents.html, invoices.html,
                       account-settings.html,
                       password-update.html,
                       mfa-settings.html, sessions.html
Admin                  admin-login.html,                 Yes (admin JWT)
                       admin-dashboard.html
Support                help-center.html, contact-us.html  No

3.3 Script Loading Strategy
----------------------------
Every page loads the full set of JavaScript files. The bootstrap.js file acts
as a page dispatcher:

    document.addEventListener('DOMContentLoaded', () => {
        // Always run: theme, smooth-scroll, nav-toggle, animations
        // Page-specific: checks window.location.pathname and calls
        // the appropriate initializer function
    });

No code splitting or lazy loading. Each page script registers its init
function on `window` and bootstrap.js calls it conditionally based on the
current URL path.

3.4 Frontend-to-Backend Communication
--------------------------------------
All API communication goes through a single apiRequest() function in
assets/js/core/api.js:

    function apiRequest(path, method = 'GET', body = null)

Features:
  - Automatically attaches JWT Bearer token from localStorage (key: aves_token)
  - Auto-detects environment: if running on port 5500/5501/3000/8080 or
    file:// protocol, targets http://127.0.0.1:8000; otherwise uses relative
    paths for production
  - Sends JSON with credentials: include
  - Auto-stores tokens received in API responses
  - Returns normalized response: { ok, message, data, status, token }

3.5 State Management
---------------------
No centralized state management (no Redux, no context, no stores).

  - Auth state:     localStorage.getItem('aves_token') (JWT)
  - Theme state:    localStorage.getItem('theme')
  - User data:      Fetched from API on page load, stored in local JS
                    variables or directly inserted into DOM
  - Server-side data is the source of truth; frontend fetches fresh data
    on every page load

3.6 CSS Architecture
---------------------
  - CSS Custom Properties for theming: light/dark mode via
    [data-theme="dark"] selector
  - Layered CSS: base.css -> layout.css -> components.css -> pages/*.css ->
    responsive.css
  - Full dark theme implementation with distinct color palettes
  - Responsive breakpoints at 1024px, 900px, 768px, and 520px
  - No CSS preprocessors (no Sass/LESS) -- pure CSS with custom properties
  - No CSS framework (no Tailwind, Bootstrap) -- all custom

4. BACKEND ARCHITECTURE
================================================================================

4.1 Server Setup
-----------------
Request flow:

    Request -> Helmet -> CORS -> JSON Parser -> Route Handler -> Response

Middleware stack (in order):
  1. helmet({ contentSecurityPolicy: false }) -- security headers
  2. Custom CORS middleware -- dynamically sets Access-Control-Allow-Origin
     to the request's origin
  3. express.json({ limit: '150kb' }) -- body parser with 150KB limit
  4. express.urlencoded({ extended: false }) -- URL-encoded body parser

4.2 Database Layer (db.js)
---------------------------
  - In-memory JSON database: reads backend/data/db.json once at startup
  - No persistence: all changes are lost on server restart
  - In serverless (Vercel), each invocation starts fresh
  - Simple auto-increment IDs: getNextId() finds max(id) + 1
  - Singleton pattern: _db variable is populated once and reused

6. AUTHENTICATION AND AUTHORIZATION
================================================================================

6.1 User Authentication
------------------------
  - Password hashed with bcryptjs (10 salt rounds)
  - On login, server returns a JWT containing { id, email, role }
  - Token stored in localStorage as 'aves_token'
  - Every authenticated request sends: Authorization: Bearer <token>
  - requireAuth middleware verifies JWT and attaches req.user

6.2 Admin Authentication
-------------------------
  - Password-only login (no username/email required)
  - Admin password verified against bcrypt hash of ADMIN_PASSWORD_SEED
  - Separate JWT issued with admin role claim
  - requireAdmin middleware checks both JWT validity and role === 'admin'

6.3 Authorization Flow
-----------------------
  - Public pages: accessible without any token
  - User pages: bootstrap.js calls AppAuth class which checks for valid
    JWT in localStorage; redirects to login.html if missing/invalid
  - Admin pages: requireAdmin middleware rejects non-admin tokens

  - Each serverless function invocation starts with the seed data
  - This is a demo/prototype setup; production would use a real database

8. KEY ARCHITECTURAL DECISIONS
================================================================================

1. Multi-Page Application over SPA:
   Simpler setup, no build step required, each page is independently
   cacheable. Trade-off: full page reloads on navigation.

2. In-Memory JSON Database:
   Zero external dependencies, simple to understand and develop with.
   Trade-off: no data persistence across server restarts or serverless
   invocations.

3. Full Script Loading on Every Page:
   No code splitting or lazy loading. Simple but means every page loads
   all JavaScript regardless of what it needs. bootstrap.js conditionally
   initializes only what the current page requires.

4. Custom CSS over Framework:
   Full control over styling with CSS custom properties. No framework
   overhead. Trade-off: more CSS to maintain, no utility classes.

5. Serverless Deployment:
   Vercel handles scaling and hosting. Trade-off: the in-memory database
   resets on cold starts, making this suitable only for demos/prototypes.

6. Separate Admin and User Auth:
   Different JWT tokens for admin and regular users. Admin uses
   password-only authentication (no email/username required).
